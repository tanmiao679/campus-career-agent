# 架构与关键流程

## 目标

项目用尽量小的工程规模展示一条完整 Agent 主链路：用户请求进入 API，模型判断是否调用工具，Java 工具执行可复现的业务逻辑，模型根据工具结果组织回答，系统同时返回脱敏执行轨迹。

## 模块边界

| 模块 | 主要类型 | 职责 |
|---|---|---|
| API | `AgentController`、请求/响应 record | HTTP 入参校验、状态码和统一响应 |
| 编排 | `CareerAgentService` | 生成请求与会话 ID、调用网关、收集轨迹、屏蔽供应商异常 |
| 模型适配 | `CareerAgentGateway`、`SpringAiCareerAgentGateway` | 隔离业务层与 Spring AI，挂载工具和会话 ID |
| AI 配置 | `AiConfig` | 系统提示词、12 条消息窗口、`ChatClient` |
| 工具 | 三个 `@Tool` 组件 | 参数二次校验与确定性业务计算 |
| 轨迹 | `ToolTraceRecorder` | 记录工具名、状态、耗时、脱敏摘要，并在请求结束后清理 |
| 可靠性 | 异常类型与全局处理器 | 把校验错误映射为 400，把模型不可用映射为 503 |

## 数据流

1. 客户端提交 `conversationId`（可选）和 `message`。
2. API 与服务层拒绝空消息或超过 8,000 字符的输入。
3. 服务层生成 `requestId`，未提供会话 ID 时生成新的 UUID。
4. `ChatClient` 向 DeepSeek 提供系统规则、会话窗口和三个工具的结构定义。
5. DeepSeek 可以不调用工具，也可以返回带结构化参数的工具请求。
6. Java 工具再次校验参数，执行确定性逻辑，并通过 `ToolContext` 取得仅供服务端使用的 `requestId`。
7. 工具结果返回模型继续生成最终回答；调用轨迹按 `requestId` 汇总进 API 响应。
8. 轨迹被读取后立即从内存中移除，避免随请求数量无限增长。

## 边界控制

- 每个工具单轮最多调用 2 次，全部工具合计最多 5 次。
- 超限策略是把错误结果返回模型，要求模型解释限制并停止继续调用。
- 工具参数有独立的空值、数量与范围校验，不能只依赖模型“自觉”。
- 供应商异常统一转成固定错误消息，不把响应体、认证头或堆栈发给客户端。
- 轨迹摘要最多 200 字符，并遮盖邮箱和中国大陆手机号。
- DeepSeek API Key 只从环境变量读取。

## 会话记忆

`MessageWindowChatMemory` 按 `conversationId` 保留最近 12 条消息。它适合演示“根据刚才的岗位继续生成计划/题目”，但不是长期用户画像：进程重启后数据消失，窗口之外的消息会被淘汰，也没有跨机器一致性保证。

## 测试分层

- 工具单元测试：覆盖解析、去重、排序、数量范围和非法参数。
- 服务测试：使用可控网关验证 ID、轨迹、输入上限和安全异常。
- API 测试：使用 MockMvc 验证 JSON 契约与 400/503 映射。
- 上下文测试：验证生产 Bean 可装配，但使用假密钥且不调用模型。
- 真实冒烟测试：只有显式提供环境变量时才启用，固定运行 5 个 DeepSeek 场景。

## 第一版为何保持小

RAG、Redis、MCP、Docker、独立前端与多 Agent 都能增加关键词，却会稀释最重要的面试主线。第一版先把 Tool Calling、上下文、调用边界、参数校验、脱敏和自动化测试做实，后续每次只增加一个能够测量收益的能力。
