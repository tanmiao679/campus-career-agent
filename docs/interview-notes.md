# 面试追问笔记

下面的回答用第一人称整理，适合作为理解框架。面试时应结合自己实际运行和调试过的细节表达，不要逐字背诵。

## 60 秒项目介绍

我做的是一个面向校招的 Java 求职 Agent。它不是把所有逻辑塞进一个大 Prompt，而是让 DeepSeek 负责识别意图、选择工具和组织回答，Java 负责三个可测试的确定性工具：JD 分析、学习计划和面试题生成。我用 Spring AI 接入 Tool Calling 和 12 条消息的会话记忆，并限制单工具最多调用 2 次、单轮最多 5 次。接口会返回脱敏的工具调用轨迹；参数错误、模型不可用和调用超限也有明确边界。项目目前有 22 个离线测试，并通过了 5 个真实 DeepSeek 场景。

## 为什么不用一个大 Prompt 完成所有事情？

大 Prompt 更快做出演示，但业务规则不稳定、结果难复现，也很难对“提取是否正确、数量是否越界、异常是否被处理”做单元测试。Tool Calling 把职责拆开：模型判断做什么，Java 工具决定怎么算。这样工具能独立测试，模型还能把多个工具组合成自然对话。

## 为什么三个工具要做成确定性逻辑？

因为岗位技能提取、学习阶段排序和题目数量都属于可验证规则。相同输入得到稳定结果，便于写测试、定位问题和控制成本。模型仍负责理解用户语言和生成最终说明，所以不是完全放弃模型能力，而是把模型用在更擅长的位置。

## `ToolContext` 有什么作用？模型能看到它吗？

我在调用 `ChatClient` 时放入 `requestId`，Spring AI 在执行 Java 工具时把它作为 `ToolContext` 注入。它不属于模型生成的工具参数，也不出现在工具 schema 中，所以模型不能伪造或覆盖它。我用这个服务端上下文把一次请求里的多次工具调用轨迹关联起来。

## 怎样防止工具无限循环？

我设置了两层硬上限：每个工具一轮最多 2 次，所有工具合计最多 5 次。达到上限时框架把错误结果交给模型，而系统提示词要求模型解释限制并停止。参数校验还会在工具入口拒绝非法范围，避免错误参数真正进入业务逻辑。

## `MessageWindowChatMemory` 保存和丢弃什么？

它按 `conversationId` 保存最近 12 条消息，让“根据刚才的 JD 继续生成计划”成立。超过窗口的旧消息会被淘汰，进程重启后内存数据也会消失。它不是数据库，也不适合长期画像或多实例共享；第一版选择它是为了把会话能力做清楚，而不是提前引入基础设施。

## 为什么第一版不使用 Redis？

Redis 能解决跨进程共享、过期策略和持久化等问题，但第一版只有单实例演示，加入 Redis 会增加安装、数据结构和一致性解释成本，却不能直接证明 Tool Calling 做得更好。我先用内存窗口验证业务链路，只有出现多实例或长期会话需求时才引入 Redis。

## 怎样保护密钥和个人数据？

密钥只从环境变量读取，`.env`、日志和构建产物都被 Git 忽略。接口不会返回供应商原始异常。工具轨迹只保存最长 200 字符的参数摘要，并遮盖邮箱和大陆手机号；请求结束后轨迹会从内存移除。我也会在提交前用敏感字符串扫描检查暂存区。

## 相比参考示例，我实际改了什么？

我参考的是 Spring AI 官方文档和 Spring AI Alibaba 示例的工具组织思路，但没有直接把示例改名。我重新设计了求职领域的三个工具、输入输出 record、技能目录、学习优先级、题库、服务网关、调用上限、会话记忆、脱敏轨迹、错误响应和分层测试，并记录了真实 DeepSeek 冒烟结果。

## 如果面试官问“为什么现在没有 RAG？”

我会直接说第一版没有实现 RAG。这个项目的目标是先证明 Agent 的工具决策、边界控制和工程质量，而不是堆关键词。下一步如果增加 RAG，我会先准备小型标注问题集，测召回率和最终回答正确率，再选择切分、Embedding、重排和向量库方案。

## 一次失败请求会怎么走？

以 DeepSeek 暂时不可用为例：模型适配层抛出异常，服务层先清理当前 `requestId` 对应的内存轨迹，再抛出固定的业务异常；全局处理器返回 HTTP 503 和 `AI_SERVICE_UNAVAILABLE`。客户端看不到认证头、供应商响应或 Java 堆栈。
